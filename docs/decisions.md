# 重要技术决策

本文记录已经体现在当前代码中的决策。未来规划只有在实现并验证后才应改为“已采用”。

## D-001：使用 Next.js App Router 组织页面与 API

- 状态：已采用
- 原因：同一项目内同时支持服务端页面、客户端交互组件和 Route Handlers，适合当前小型全栈 MVP。
- 结果：页面位于 `src/app`，Diary JSON API 和 Better Auth 入口也使用 Route Handlers。

## D-002：使用 TypeScript

- 状态：已采用
- 原因：为页面属性、Diary 输入输出和服务调用提供静态类型检查，并由 Next.js 生产构建统一验证。

## D-003：使用 Prisma 作为数据访问层

- 状态：已采用
- 原因：集中定义模型、关系、唯一约束和迁移，并为服务端查询提供类型安全的客户端。
- 结果：常规查询使用 Prisma ORM；行锁和 Dashboard 聚合使用 Prisma 标签模板参数化 SQL，用户值不拼接进 SQL 文本。数据库变化通过 `prisma/migrations` 追踪。

## D-004：MVP 使用 SQLite

- 状态：历史方案，当前正式环境为 Render + Neon PostgreSQL
- 原因：早期本地开发简单，先完成产品闭环和多人隔离验证。
- 限制：SQLite 文件不适合多实例云端共享，归档 migration 和导出工具只用于追溯/隔离演练，不用于当前 Neon 的 v2.4 增量发布。

## D-005：使用 Better Auth 管理认证

- 状态：已采用
- 原因：避免自行实现密码散列、Session Token 和 Cookie 管理，并可通过 Prisma Adapter 复用当前数据库层。
- 结果：当前提供邮箱密码注册、登录、退出和 Session 获取；认证数据使用 `User`、`Session`、`Account` 和 `Verification` 模型。

## D-006：用户身份只能来自服务端 Session

- 状态：已采用
- 原因：如果信任客户端传入的 `userId`，用户可以伪造身份访问他人数据。
- 结果：Route Handler 和服务端页面先调用 `getCurrentUser()`，再把 `user.id` 传给 Diary 服务；客户端身份字段不参与查询或写入。

## D-007：Diary 使用 `(userId, date)` 复合唯一约束

- 状态：已采用
- 原因：业务规则是“每位用户每天一篇”，而不是“整个系统每天一篇”。
- 结果：同一用户同一天重复保存时 upsert 原 Diary，不同用户可以在同一天分别记录。

## D-008：所有 Diary 查询都在服务层显式限定用户

- 状态：已采用
- 原因：将隔离规则放在统一数据访问边界，避免页面或 API 漏掉权限条件。
- 结果：今日、历史、搜索和详情查询全部带有 `userId`；详情查询不到他人记录时返回 404，而不是泄露记录存在性。

## D-009：按用户时区计算日期键

- 状态：已采用
- 原因：服务器时区不能代表所有用户的“今天”，在跨地区日期边界会创建或读取错误日期的 Diary。
- 结果：`User.timeZone` 默认 `Asia/Shanghai`；服务端校验时区，并使用 `Intl.DateTimeFormat` 计算 `YYYY-MM-DD`。今日读取、存在判断和保存使用同一个日期键。

## D-010：多人迁移必须保留单用户数据

- 状态：已采用
- 原因：加入用户系统不应丢失已经积累的 Diary。
- 结果：迁移保留原 Diary 的 ID 和内容，并为旧数据指定已有用户或创建迁移专用用户；随后把唯一约束改为 `(userId, date)`。

## D-011：保留未使用的 `Diary.content` 字段

- 状态：当前保留
- 原因：该字段来自初始模型，已有迁移和数据包含它。当前三个结构化字段已经满足界面需要，本阶段没有业务理由修改或删除它。
- 结果：创建 Diary 时写入空字符串，但 API 与页面不返回或编辑该字段。若未来清理，需要单独迁移和数据评估。

## D-012：发布前验证数据隔离和构建

- 状态：已采用
- 原因：认证和隔离错误的影响高于普通界面问题。
- 结果：当前测试覆盖两位用户注册、Session、Diary 隔离、他人详情 404、搜索隔离和上海/东京日期边界；功能变更还需通过 ESLint 和生产构建。

## D-013：个人设置更新继续使用 Session 身份边界

- 状态：已采用
- 原因：用户资料与 Diary 一样属于用户私有数据，允许客户端指定 `userId` 会形成越权更新风险。
- 结果：`/settings` 只展示当前用户资料；设置 API 从 Better Auth Session 获取用户 ID，只允许修改用户名和时区，并明确拒绝请求体中的 `userId`。邮箱在本阶段只读。用户名和 IANA 时区都在服务端校验。
